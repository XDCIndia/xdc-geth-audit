XDC Porting Guide

Reconstructing the XDC overlay on a fresh geth release — generated from branch reset/integration-1.17.3 at commit 8337f48ec, fork base 117e067f0 (geth v1.17.3). Scope: 262 files, +69,413 / -412 lines, 243 commits.

This document records every XDC-specific change applied on top of pristine go-ethereum v1.17.3 (commit 117e067f0f0bae1a17082321f224dedb6765b10f) to produce the head of branch reset/integration-1.17.3. The intended audience is an engineer (human or AI) tasked with applying the same overlay to a future upstream tag — e.g. v1.18.x, v2.0. Every claim below is grounded in the actual files present in the tree; line numbers and quoted snippets were re-read at the time of writing.

1. Executive summary #

XDC Network is a delegated-PoS chain forked from Ethereum. It uses two consensus generations:

  • XDPoS V1 — Clique-style round-robin leader rotation over a 108-node masternode set. Epoch length 900 blocks. Used from genesis to a per-network V2.SwitchBlock.
  • XDPoS V2 — HotStuff-derived BFT with QuorumCerts, votes, timeouts. Switches in mid-chain (mainnet block 80,370,000, Apothem block 56,828,700). Reward distribution, masternode rotation, and finality flow change at the switch.

This port adds:

  1. The XDPoS engine (V1 + V2) under consensus/XDPoS/....
  2. XDC-specific chain configs and 80+ trusted-sync checkpoints in params/config.go.
  3. Embedded genesis JSON with pre-deployed validator/blocksigner/randomize smart contracts.
  4. A custom XDPOS/100 wire protocol that coexists with upstream ETH/69 + ETH/70 on the same eth capability.
  5. A pre-merge sync loop (eth/sync_xdc.go, ~1240 lines).
  6. An RPC namespace XDPoS_* plus eth_* extensions.
  7. ~30 XDC: bypass log call-sites in core/* and eth/*.
  8. Solidity-derived Go bindings for XDPoS system contracts.

The branch HEAD 8337f48ec is not at full consensus parity with canonical XDPoSChain v2.6.8. See docs/port/CONSENSUS_PARITY.md and docs/port/STATUS.md. The port is M3-blocked on peer-fleet snapshot indexing; consensus-rule mismatches are tracked inline as XDC: comments and as ADRs under docs/adr/.

2. Prerequisites & skills required #

  • Go, including modern generics (geth v1.17.x uses lru.Cache[K,V], rlp.RawList[T]).
  • go-ethereum internals: core.BlockChain, core/state.StateDB, eth/downloader, eth/protocols/eth, eth/protocols/snap, the consensus.Engine interface (now also consensus.CacheInvalidator).
  • Ethereum consensus model: header layout, RLP encoding, trie / pathdb, receipt-root / state-root semantics, EIP-2929/3529/3860 gas rules, EIP-1559 base-fee semantics, EIP-2565 MODEXP pricing.
  • XDPoS BFT specification: rounds, QuorumCerts, TimeoutCerts, epoch-switch headers, the "M1 (signers)" and "M2 (validators)" double-signing scheme used in V1, masternode set computation via the Validator (0x88), BlockSigner (0x89), and Randomize (0x90) contracts.
  • Cryptography: secp256k1 ECDSA crypto.Sign / crypto.Ecrecover. BLS is not used — XDPoS V2 uses k-of-N ECDSA signatures over the QC payload, not aggregate signatures.
  • Solidity for reading/regenerating XDPoS system-contract bindings under contracts/.
  • Git rebase + merge workflows: the original port used a bundle-merge mechanic (B0..B11) preserving 677 SHAs while presenting ~12 reviewable units. See docs/PORT_LOG.md.

5. Subsystem-by-subsystem changes #

5.a Chain configuration & params

Why

XDC mainnet and Apothem each have their own chain ID, fork schedule, masternode bootstrap list, and XDPoS-specific V2 round configuration. Several "EIPs" that upstream couples to a single fork block are split across two on XDC (e.g. EIP-2929/3529/3860 land at Eip1559Block, not Berlin/London/Shanghai).

How the patterns work

XDCMainnetChainConfig in params/config.go:200 sets ChainID=50, fork blocks aligned with XDPoSChain v2.6.8 mainnet constants, and an XDPoSConfig{Period:2, Epoch:900, Reward:5000, RewardCheckpoint:900, Gap:450, FoudationWalletAddr:0x92a289...}. The V2 block is 80,370,000 on mainnet, 56,828,700 on Apothem.

TrustedSyncCheckpoints is a per-network array of pre-verified {Number, Hash, Root, Masternodes, Penalties} quadruples. V2-era anchors (post-V2-switch) carry the embedded masternode list as well, because V2 headers do not carry it in header.Validators.

Rules{IsXDC, IsEIP1559, IsEIP3860} carry XDC-aware EVM rule flags. EIP-2929/3529/3860 are deferred to Eip1559Block on XDC, not Berlin/London/Shanghai:

isEIP2929 := c.IsBerlin(num) && !isVerkle
if c.IsXDC() {
    isEIP2929 = c.IsEIP1559(num) && !isVerkle
}
...
if c.IsXDC() {
    isMergeRule = c.IsLondon(num)
    isShanghai  = c.IsLondon(num)
    isCancun    = c.IsCancunBlock(num)
    isEIP3860   = c.IsEIP1559(num)
}

IsXDC() at params/config.go:2665 is the single discriminator: true iff c.XDPoS != nil. This replaces ~11 historical hard-coded chainID == 50 || chainID == 51 sites.

The TIP fork-block globals in common/types.go:97-122 are package-level *big.Int defaults set to mainnet values; common.CopyXDCConstants(chainID) mutates them at engine wiring time. This is a load-bearing global-mutation pattern: any test that touches these constants must call CopyXDCConstants with the right chain ID first.

When applying to a future geth

  • Rules struct: upstream may add new flags (Verkle, Amsterdam, Pectra). Re-thread IsXDC / IsEIP1559 / IsEIP3860.
  • ChainConfig.CheckConfigForkOrder: XDC config sets Constantinople == Petersburg == Istanbul == Berlin == London on mainnet (76_321_000). Keep these tied.
  • Eip1559Block is XDC-specific (not standard geth); preserve it.
  • XDPoS.V2.BuildConfigIndex() is called from the engine New() after AllConfigs is populated.

5.b Genesis

Why

XDC chains require three system contracts pre-deployed at addresses 0x88 (Validator/MasternodeVoting), 0x89 (BlockSigners), 0x90 (Randomize). The mainnet genesis state contains the initial 108 masternode set encoded into validator-contract storage. The genesis header's extraData carries an extraVanity (32 bytes) || signers || extraSeal (65 bytes) block, the V1 signer encoding.

5.d Block validation & types

Why

5.e State, precompiles, and the EVM jump table

Why

XDC defers several EIPs from the upstream blocks geth ties them to:

  • EIP-2929 (cold/warm access lists): geth at Berlin → XDC at Eip1559Block.
  • EIP-3529 (refund cap reduction): geth at London → XDC at Eip1559Block.
  • EIP-3860 (initcode word cost): geth at Shanghai → XDC at Eip1559Block.
  • EIP-2565 (cheaper MODEXP): geth at Berlin → XDC at Eip1559Block.
  • EIP-2028 (calldata gas reduction): unconditionally disabled on XDC.

5.f Sync layer

Why

Upstream v1.17.3 dropped the pre-merge chainSyncer. Its sync model is now BeaconSync(head, final) driven by a consensus-layer forkchoiceUpdated. XDC has no consensus layer; the BFT consensus is self-contained inside the masternode set. After the first BeaconSync round the downloader idles.

The fix is a dedicated pre-merge sync loop (xdcSyncer) plus a state machine that gates --syncmode snap engagement against the XDC peer fleet's snap readiness.

9. Pitfalls & "don't do this" #

9.1 Consensus correctness is sacred

Never "improve" XDPoS rules during port work. Specifically:

  • Do not modify reward calculation, masternode selection, or epoch boundaries.
  • Do not change RLP encoding of any block / header / receipt field.
  • Do not force upstream defaults onto XDC-customised paths.
  • Treat hash mismatch as P0 — stop everything until root-caused.

9.2 The "XDC:" markers are load-bearing

Removing or "cleaning up" any XDC: log line will likely produce a state-root divergence at a future block. The markers identify exactly where canonical XDPoSChain v2.6.8 behaviour differs from upstream Ethereum validation.

9.3 V1 → V2 hardfork boundary is high-risk

At mainnet block 80,370,000:

  • The trie must be force-committed (core/blockchain.go:1788).
  • V1 snapshot logic stops applying; V2 snapshot store activates.
  • header.Validators (V1 M2 signers) becomes empty.
  • Reward distribution moves from Number % 900 == 0 to epoch-switch-keyed.
  • The first V2 block (V2.SwitchBlock + 1) skips reward distribution entirely.

The TrustedSyncCheckpoint at 80,370,000 mainnet is "Path B": its Masternodes field is populated so InsertHeadersBeforeCutoff can pre-seed the V2 snapshot store without needing contract state. Without that pre-seed, the engine fails verification of the very next block.

9.4 BigBalance is a 4-file invariant

The BigBalance overflow path lives in:

  • core/types/state_account.go
  • core/state/state_object.go
  • core/state/snapshot/{disklayer,difflayer}.go
  • core/state/reader.go
  • trie/secure_trie.go
  • triedb/pathdb/reader.go

If you touch any one, audit the others. The historical divergence cases (#793/#794/#795/#796) all traced to one half of the pair being updated without the other.

9.5 Snap-sync semantics are subtle

Read docs/port/MENTAL_MODEL.md before touching eth/sync_xdc.go. The two-pivot model (xdcSyncer pivot vs downloader pivot) is the most common source of incorrect bug-fixes.

fsMinFullBlocks controls the downloader's pivot offset from head. It is not a knob for pinning any other pivot. The downloader pivot is always head − fsMinFullBlocks — the only way to relocate it is to relocate head.

9.6 XDC peer fleet does not currently serve snap

As of STATUS.md, the XDC peer fleet has not generated a snap-protocol snapshot index. The --syncmode snap path will engage but ultimately fall back to FULL_SYNC via Phase 14.4 stall detection. This is expected behaviour until task #96 is done.

9.7 The blacklist is hardcoded and chain-specific

common/types.go:126 holds a 57-address blacklist used at all blocks ≥ BlackListHFNumber (mainnet: 38,383,838; Apothem: 23,779,191). Both sender and recipient are checked. Do not remove entries.

9.8 The common.TIP* globals are mutated at runtime

common.CopyXDCConstants(chainID) mutates package-level *big.Int globals. Called once during engine construction. Never call it twice with different chain IDs in the same process — tests exercising both mainnet and Apothem in one binary will alias the latter on top of the former.

9.9 The Foudation typo

common/xdc_contracts.go:32: FoudationAddrBinary (missing 'n') is intentional. The historical misspelling propagated through canonical XDPoSChain, exported APIs depend on it, and a fix would touch ~20 sites.
