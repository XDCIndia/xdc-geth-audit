1. What this document is

This is a runbook for porting XDC Network's consensus changes on top of any future upstream geth version. Read it once end-to-end before starting; refer back during the work.

Audience A developer who can read Go and use git, but has never touched XDC's fork before. By the end you should be able to take upstream/v1.18.0 (or whatever the next geth release is) and produce a working XDC-compatible binary that syncs Apothem from genesis.

What changes between geth releases that matters to XDC

  • State encoding — upstream may change StateAccount layout, RLP encoding, or trie database API. XDC's BigBalance support must adapt.
  • Sync engine — upstream moved to post-merge BeaconSync. XDC is pre-merge and needs its own continuous sync loop.
  • Wire protocol — upstream evolves eth/68+. XDC peers speak XDPOS2/100 which is eth/63-shaped.
  • EVM/precompiles — upstream adds new EIPs at each fork; XDC selects which ones to adopt.
  • BlobSchedule, BlobPool, History pruning, PBSS — ongoing upstream work that XDC needs to interop with without breaking consensus.

Outputs of a successful port

  1. ./build/bin/geth --chain=apothem binary that syncs Apothem from genesis to head with zero BAD BLOCK records.
  2. Per-block hash parity with https://erpc.apothem.network verified by scripts/validate-canonical-parity.sh.
  3. Same for mainnet against https://explorer.xinfin.network.
  4. go build ./... + go vet + touched-package go test -short all green.

4. Port strategy — rebase or merge?

You have three options when a new upstream geth release lands. Pick early; the choice is hard to reverse.

StrategyWhat it isWhen to chooseRisk
Big-bang reset Start from upstream/vX.Y.Z, cherry-pick the XDC overlay bundle-by-bundle You're >100 commits behind upstream and XDC has accumulated >500 overlay commits with conflicts Days of conflict resolution; some XDC behaviours may need redesign
Incremental merge Merge upstream tag-by-tag, run parity harness between each You're 1-3 minor versions behind and overlay has stayed clean Slow but predictable; each merge is small
Freeze Stay on current upstream base, only backport security fixes Upstream API has churned hard (e.g. post-merge transition) and your overlay can't keep up Falls further behind, harder to catch up later
Real-world example Issue #740 used big-bang reset — XDC's xdc-network branch was 676 commits ahead of pre-1.17.0 base, with significant state divergence rot. The team did a clean reset onto v1.17.3 and re-applied the consensus overlay. See docs/port/HANDOFF.md.

Decision tree

How far behind upstream are you?
├── <30 commits or <1 minor version
│   └── Incremental merge — merge each release tag separately
├── 30-300 commits or 1-2 minor versions
│   ├── Has the API churned heavily? (state, downloader, txpool)
│   │   ├── Yes → Big-bang reset
│   │   └── No  → Incremental merge
└── >300 commits or >2 minor versions
    └── Big-bang reset (almost always cheaper than walking 300 commits)

5. How to identify XDC modifications in any codebase

Before you can port, you must see what's XDC and what's upstream. XDC uses consistent markers.

The four marker conventions

MarkerExampleMeaning
XDC: comments // XDC: ... Every non-trivial XDC change is preceded by a // XDC: comment explaining what differs and why. Grep these first — they're the single best map.
config.XDPoS if config.XDPoS != nil { ... } Most consensus-critical changes branch on chainConfig.XDPoS != nil so they're inert on non-XDC chains.
IsXDC() config.IsXDC() or rules.IsXDC Convenience accessor — equivalent to config.XDPoS != nil. Used in core/vm, txpool, etc.
XDC-prefixed names XDCBaseFee, XdcAgent, PrecompiledContractsXDCBerlin, XdcBulkSyncMode Types, constants, and functions added by XDC. Always prefix-named.

Quick survey commands

# Count XDC markers
grep -r "// XDC:" --include="*.go" . | wc -l       # ~47 in this branch
grep -rE "config\.XDPoS\s*!=\s*nil" --include="*.go" . | wc -l   # ~40
grep -r "IsXDC()" --include="*.go" . | wc -l        # ~11
grep -rE "type XDC|func.*XDC[A-Z]" --include="*.go" . | wc -l    # ~428

# Files modified by XDC overlay (range = upstream base..XDC HEAD)
git diff <upstream-base>..HEAD --name-only | grep "\.go$" | sort | uniq

# XDC-only files (didn't exist in upstream)
git diff <upstream-base>..HEAD --name-only --diff-filter=A | grep "\.go$"

# Most-touched directories
git diff <upstream-base>..HEAD --name-only | grep "\.go$" | awk -F/ '{print $1"/"$2}' | sort | uniq -c | sort -rn

The "find the smoking gun" workflow

  1. Build the new upstream version cleanly (no XDC overlay). Confirm it builds.
  2. Apply XDC overlay file-by-file. After each file: go build ./....
  3. When build breaks: the upstream API signature changed under your overlay. Use the marker comments to understand what XDC was trying to do, then re-attach to the new API.
  4. Common shifts: function signatures, struct field names, interface methods. Search for the intent, not the syntax.

6. Subsystem-by-subsystem reference

Each subsystem below has: what XDC adds, key files, how to detect upstream breakage, how to fix.

6.1 — Consensus engine (consensus/XDPoS)

What XDC adds

  • XDPoS V1 engine: round-robin masternode selection per epoch (900 blocks on Apothem).
  • XDPoS V2 engine: BFT with Quorum Certificates (QC), 3-chain finality, Vote/Timeout/SyncInfo messages.
  • Hooks: HookReward (epoch-switch reward distribution), HookPenalty (masternode penalty for missed blocks), HookCommitBlock (V2 finality marking).

Key files

consensus/XDPoS/xdpos.go consensus/XDPoS/engines/engine_v1/engine.go consensus/XDPoS/engines/engine_v2/engine.go consensus/XDPoS/engines/engine_v2/{vote,timeout,epochSwitch,forensics}.go eth/hooks/hooks.go eth/hooks/engine_v2_hooks.go

Upstream-breakage signals

  • consensus.Engine interface gained/lost methods → XDPoS wrapper won't implement it. Update xdpos.go.
  • consensus.ChainHeaderReader / ChainReader signatures change → hook closures need updating.
  • StateDB shape changes → HookReward signature breaks (state, parentState are *state.StateDB).

How to port

  1. Run go build ./consensus/XDPoS/... against new upstream — fix any signature mismatches.
  2. Verify eth/backend.go still casts eth.engine.(*XDPoS.XDPoS) successfully.
  3. Confirm xdposEngine.SetEngineV2(v2Engine) wiring still compiles.
  4. Run go test ./consensus/XDPoS/...; if test files reference old upstream APIs, update them.
6.2 — State (StateAccount, BigBalance)

What XDC adds

  • StateAccount.BigBalance *big.Int with rlp:"-" tag — for balances exceeding 2^256-1.
  • Hand-written EncodeRLP/DecodeRLP in core/types/gen_account_rlp.go replacing the auto-generated version.
  • types.DecodeSlimAccount that returns BigBalance when blob represents an oversize value.
  • Defensive recover() wrappers in trie/snapshot/PBSS readers.

Key files

core/types/state_account.go core/types/gen_account_rlp.go trie/secure_trie.go core/state/snapshot/disklayer.go core/state/snapshot/difflayer.go core/state/reader.go triedb/pathdb/reader.go

Upstream-breakage signals

  • If upstream changes StateAccount layout, your hand-written EncodeRLP/DecodeRLP must be updated.
  • If upstream adds a new state reader (e.g. cachingDB), it may bypass your BigBalance decode → sync panics on first oversize account.
  • Watch for any new rlp.DecodeBytes(blob, &types.SlimAccount{}) calls in upstream code paths.

How to port

  1. Diff core/types/state_account.go: ensure any new field gets handled by EncodeRLP/DecodeRLP.
  2. Grep new upstream for rlp.DecodeBytes(...SlimAccount; replace with types.DecodeSlimAccount.
  3. Test: run scripts/validate-canonical-parity.sh on a sync that crosses block 2700 (Apothem) — that's the historical canary.
6.3 — Sync engine

What XDC adds

  • xdcSyncer: continuous loop fetching xdcBatchSize=4096 headers + bodies direct from peers, calling blockchain.InsertChain.
  • core.XdcBulkSyncMode: atomic.Bool global; sync-time fast-paths gate on it.
  • Custom Peer.XDCHeaderResp / XDCBodyResp channels bypassing the eth/68 dispatcher (XDPOS2 messages have no RequestId).
  • downloader.Synchronising() public accessor; beaconsync.go zero-cutoff guard.

Key files

eth/sync_xdc.go eth/handler.go (xdcSync field) eth/handler_xdc.go (broadcast functions) eth/downloader/downloader.go (Synchronising) eth/downloader/beaconsync.go (zero-cutoff guard)

Upstream-breakage signals

  • Upstream replaces or removes BeaconSync → verify xdcSyncer still has a place to live.
  • blockchain.InsertChain signature changes → xdcSyncer.maybeSync won't compile.
  • New downloader stage added → verify it respects XdcBulkSyncMode if it has consensus implications.

How to port

  1. Check eth/handler.go still calls h.xdcSync = newXDCSyncer(h) in Start() and h.xdcSync.stop() in Stop().
  2. Verify peer.XDCHeaderResp/XDCBodyResp channels still exist on *eth.Peer.
  3. Test with a fresh-wipe sync from genesis.
6.4 — EVM (precompiles, instruction sets, base fee)

What XDC adds

  • PrecompiledContractsXDCBerlin: same as upstream Berlin but with bigModExp{eip2565: false}. Selected when rules.IsXDC && !rules.IsEIP1559.
  • XDC instruction set variants: newXDCBerlinInstructionSet (= Istanbul, no EIP-2929), newXDCLondonInstructionSet (+EIP-3198), newXDCMergeInstructionSet (+PREVRANDAO), newXDCShanghaiInstructionSet (+PUSH0).
  • Fixed XDCBaseFee = 12,500,000,000 wei (12.5 gwei) for XDPoS chains.
  • EIP-2028 disabled in core.IntrinsicGas when chain config IsXDC().

Key files

core/vm/contracts.go core/vm/jump_table.go core/vm/evm.go consensus/misc/eip1559/eip1559.go params/protocol_params.go (XDCBaseFee) core/txpool/validation.go (EIP-2028 gate)

Upstream-breakage signals

  • New precompile added at Cancun/Prague/Osaka → verify XDC's fall-through (XDC inherits standard Cancun+ precompile sets at the Cancun fork).
  • IntrinsicGas signature changes → the isEIP2028 bool parameter may shift position.
  • EIP-1559 verification path refactored → XDC's feeMarketActive helper may need re-attaching.

How to port

  1. Diff core/vm/contracts.go's activePrecompiledContracts; ensure the rules.IsBerlin arm still branches to PrecompiledContractsXDCBerlin when rules.IsXDC && !rules.IsEIP1559.
  2. Verify IntrinsicGas caller in core/txpool/validation.go still passes isEIP2028=false for XDC chains.
  3. Verify VerifyEIP1559Header + CalcBaseFee in consensus/misc/eip1559/eip1559.go still branch on config.XDPoS != nil.
6.5 — Wire protocol (XDPOS2 + V2 BFT messages)

What XDC adds

  • Protocol-version negotiation: production XDC peers speak XDPOS2/100 which uses bare eth/63 message shapes (no RequestId envelope).
  • StatusPacket62 5-field handshake (no Genesis or ForkID fields).
  • Bare-shape branches in RequestHeadersByHash/ByNumber, RequestBodies, and the inbound handlers.
  • V2 BFT message codes VoteMsg=0xe0, TimeoutMsg=0xe1, SyncInfoMsg=0xe2 with payload-only packets.
  • Per-peer bypass channels (XDCHeaderResp, XDCBodyResp) so XDPOS2 responses don't need the eth/68 dispatcher.

Key files

eth/protocols/eth/protocol.go (msg codes + packets) eth/protocols/eth/peer.go (XDC channels + branching) eth/protocols/eth/handlers.go (decode + dispatch) eth/protocols/eth/handler.go (handler map) eth/protocols/eth/handshake.go (StatusPacket62) eth/handler_eth.go (V2 BFT accept)

Upstream-breakage signals

  • eth protocol bumped to eth/69+: verify the XDPOS2 branch still triggers based on protocol version, not eth/68.
  • Packet types renamed (e.g. NewBlockHashesPacket removed post-merge): keep the XDC handler stubs.
  • Per-peer channel buffering may need adjustment if upstream changes peer goroutine model.
6.6 — Genesis + chain config

What XDC adds

  • Two chain configs in params/config.go: XDCMainnetChainConfig (chain ID 50), XDCApothemChainConfig (chain ID 51).
  • XDPoSConfig struct with Epoch, RewardCheckpoint, V2 sub-config, TrustedSyncCheckpoints, etc.
  • patchMissingForkBlocks in core/genesis.go — fills in fork blocks that older genesis JSONs may have missed.
  • Apothem-specific fork constants: TIPSigning at 23,779,191; V2 switch at 56,828,700; Berlin/EIP-1559 at 61,290,000.

Key files

params/config.go (XDC* configs) core/genesis.go (patchMissingForkBlocks) consensus/XDPoS/constants.go common/types.go (TIPSigning, BlockSigners, BlackListHFNumber)

Upstream-breakage signals

  • New BlobScheduleConfig field added → verify XDC chains either nil or have placeholder. See the UBT alias precedent.
  • New Rules field → XDC chains should have safe default.
  • ChainConfig.IsXXX(num) method signature changes → XDC's IsXDC(), IsEIP1559(), etc. must match the new pattern.
6.7 — Forks (TIPSigning, V2 switch, BlackList HF)

What each fork does

  • TIPSigning (Apothem 23,779,191) — SelfDestruct the BlockSigners contract at 0x89. Wiped multi-gigabyte storage trie that was prohibitively large. core/state_processor.go handles this.
  • BlackListHF (Apothem 23,779,191) — mempool starts rejecting txs from/to blacklisted addresses. core/txpool/legacypool/legacypool.go.
  • V2 switch (Apothem 56,828,700) — consensus transitions from V1 (round-robin) to V2 (BFT). Block 56,828,700 itself uses V1 format. core/blockchain.go writeBlockWithState forces a state trie commit at this block.

Key files

core/state_processor.go (TIPSigning wipe) core/blockchain.go (V2 commit + P1 epoch commit) core/block_validator.go (early-block + checkpoint tolerance) consensus/XDPoS/constants.go (fork block constants)

6.8 — Backend wiring (eth/backend.go)

What XDC adds

This is the highest-leverage file in the port. eth/backend.go must:

  1. After LoadChainConfig: common.CopyXDCConstants(chainID) + XDPoS.SetNetworkConstants(chainID) — so the engine + downstream see consistent values.
  2. After NewBlockChain: cast eth.engine to *XDPoS.XDPoS, call AttachConsensusV1Hooks + AttachConsensusV2Hooks.
  3. If V2 is configured: construct engine_v2.New(...), wire HookCommitBlock, call SetEngineV2, then forward HookReward via SetHookReward.

Without this

XDPoS.EngineV2 stays nil at runtime. V2 blocks pass through V1 light-verify fast path: no QC checks, no reward distribution, no BFT finality.

// XDC: attach XDPoS V1 + V2 consensus hooks
if xdposEngine, ok := eth.engine.(*XDPoS.XDPoS); ok {
    hooks.AttachConsensusV1Hooks(xdposEngine, eth.blockchain, chainConfig)
    hooks.AttachConsensusV2Hooks(xdposEngine, eth.blockchain, chainConfig)

    if chainConfig.XDPoS != nil && chainConfig.XDPoS.V2 != nil {
        v2Engine := engine_v2.New(chainConfig, chainDb, nil, nil)
        v2Engine.HookCommitBlock = func(header *types.Header) {
            eth.blockchain.SetFinalized(header)
        }
        xdposEngine.SetEngineV2(v2Engine)

        xdposCapture := xdposEngine
        v2Engine.SetHookReward(func(chain consensus.ChainReader, ...) {
            return xdposCapture.HookReward(chain, ...)
        })
    }
}

7. The step-by-step playbook

This is the sequence to follow when porting onto a new upstream version. Allow ~3-7 days of focused work for a typical port.

1

Snapshot current state

  • git branch xdc-network-pre-reset origin/xdc-network — rollback insurance.
  • Take Apothem+mainnet chaindata snapshots (one per node type: full, snapfull, archive, fullpath, snapfullpath, archivepath, snappath).
  • Push the pre-reset branch to remote, retain 30 days.
2

Triage the upstream gap

  • git fetch upstream --tags
  • git log --oneline <old-base>..<new-tag> | wc -l — commit count gap.
  • git diff <old-base>..<new-tag> --stat — identify churned areas.
  • Bucket each commit (A=docs, B=consensus, C=execution, D=p2p, E=test/CI, F=collision with XDC overlay).
3

Pick strategy

Big-bang reset, incremental merge, or freeze (see section 4). Document choice in docs/port/UPSTREAM_CATCHUP.md with reasoning.

4

Reset branch (if big-bang)

  • git checkout -b reset/<new-tag> <new-tag>
  • Verify it builds: make geth
  • Verify go test ./... -short passes against pristine upstream.
5

Enumerate XDC overlay commits

  • git log --oneline <old-base>..xdc-network > /tmp/xdc-overlay.txt
  • Group commits into bundles by subsystem (B1 XDPoS, B2 state, B3 EVM, B4 wire, B5 P1 bulk sync, B6-state-Fbucket, B7 blockchain, etc.).
  • Document bundle order in docs/port/RESET_BUNDLES.md.
6

Apply bundles, parity-gate each

For each bundle in order:

  1. Cherry-pick or git-merge the bundle commits.
  2. Resolve conflicts. XDC behaviour wins where the XDC: marker is present.
  3. go build ./... && go vet ./... — must be green before continuing.
  4. Run touched-package go test -short.
  5. For consensus-critical bundles (XDPoS, state, blockchain): run scripts/local-sync-test.sh wipe-stateful && start all + grep for failure markers (see section 9).
  6. Commit the bundle with a clear subject: xdc: port <bundle> onto vX.Y.Z.
7

Run full validation suite

See section 8. The acceptance gate is scripts/validate-canonical-parity.sh showing N/N match against canonical Apothem.

8

Document the port

  • Update docs/port/HANDOFF.md with commit list, validation results, deferred items.
  • Regenerate docs/port/XDC_PORT_STATUS.html (drop in the new file list).
  • Open a tracking issue in XDCIndia/go-ethereum using the validation-plan template (see issue #798).
9

Deploy + soak

Section 11 has the full deployment procedure. Briefly: xdc02 first (existing chaindata recovery), then xdc04 (fresh sync from genesis), then 7-day soak, then mainnet bring-up on isolated host.

8. Validation strategy

Three tiers of validation, in order of strength.

Tier 1: build + vet + tests

cd /path/to/go-ethereum
go build ./...           # must be exit 0
go vet ./...             # must be exit 0 (or only pre-existing failures)
go test -short -count=1 -timeout 120s \
  ./common/... \
  ./params/ \
  ./consensus/XDPoS/... \
  ./consensus/misc/eip1559/ \
  ./core/vm/ \
  ./core/txpool/... \
  ./internal/web3ext/
# All packages: ok

Tier 2: local-sync-test cluster

scripts/local-sync-test.sh runs 8 nodes (full, snapfull, archive, snap + path-scheme variants) on one host, sourcing from each other. Used as a smoke test after every consensus-critical bundle:

./scripts/local-sync-test.sh wipe-stateful
./scripts/local-sync-test.sh start all
# Watch logs for 30+ minutes
./scripts/local-sync-test.sh status
# Grep for failure markers
grep -E "BAD BLOCK|invalid merkle root|XDC TIPSigning state-root bypass|XDC: Setting head" nodes-local/*.log
# Expected: zero matches

Tier 3: canonical parity (the real gate)

scripts/validate-canonical-parity.sh compares block hashes byte-for-byte against https://erpc.apothem.network or https://explorer.xinfin.network:

# Quick mode: fixed milestones only
./scripts/validate-canonical-parity.sh \
  -i nodes-local/snapfullpath/geth.ipc \
  -r https://erpc.apothem.network \
  -q

# Full mode: 30 random samples plus milestones
./scripts/validate-canonical-parity.sh \
  -i nodes-local/snapfullpath/geth.ipc \
  -r https://erpc.apothem.network \
  -s 30

# Acceptance: PASS  N/N blocks matched
Real result On fix/pathdb-rlp-import branch (the v1.17.3 reset): 38/38 random+fixed blocks PASS from genesis to head 15.99M. Including block 1 — which proves XDC genesis hash is canonical-correct.

What to do when parity fails

  1. Note the first failing block N.
  2. Run ./scripts/validate-canonical-parity.sh -d ... (deep mode: compares receipts too) to narrow stateRoot vs txRoot vs receiptsRoot.
  3. If stateRoot diverges: state encoding bug (BigBalance? EIP-2028 enabled by mistake? MODEXP gas?). Walk the block's transactions one at a time.
  4. If txRoot diverges: transaction encoding bug or wrong signer set.
  5. If receiptsRoot diverges: gas-used or log-bloom mismatch.
  6. If hash diverges but the three roots match: header field issue (extraData, mixDigest, gasLimit elasticity).

9. Gotchas and common pitfalls

P0 Consensus parity mismatch is sacred. Stop everything until root-caused. Never "optimise" consensus paths until bit-perfect parity is verified.

Things that have bitten us before

PitfallSymptomFix
BigBalance decode path missed in a new upstream reader (e.g. PBSS reader added in v1.17.3) Sync panics at block 2700 (or first BigBalance account) with rlp: value too large for uint256 Grep new reader paths for rlp.DecodeBytes(...&SlimAccount), replace with types.DecodeSlimAccount. Reference fix: PR #796.
Upstream removed NewBlockHashesPacket / NewBlockPacket post-merge XDPOS2 peers send these (codes 0x01, 0x07) and the handler drops them as "unknown packet" Add stubs handleNewBlockhashesXDC + handleNewBlockXDC in protocol layer (eth/protocols/eth/handler.go); accept-and-ignore at handler_eth.go.
Over-aggressive IsLondon → IsEIP1559 swap Upstream chains (without XDPoS config) reject post-London blocks as "invalid baseFee" Use a feeMarketActive(config, num) helper that returns IsEIP1559 for XDPoS chains, IsLondon for upstream. Reference fix: commit 69a644d2f.
StateAt signature changed (upstream took common.Hash, now takes *types.Header) V2 engine's repairSnapshot silently falls through — candidate lookup never happens Update the interface assertion in consensus/XDPoS/engines/engine_v2/engine.go. Reference fix: commit 022c9b199.
Upstream test added a new BlobScheduleConfig field; tests reference it by XDC name (e.g. UBT) but struct has it under upstream name (e.g. Verkle) go test ./core/ fails to build Add an alias field. The existing UBT-as-Verkle pattern in ChainConfig is the precedent. Reference fix: commit 1c12e6a2e.
V2 engine never constructed at runtime (XDPoS.EngineV2 nil) V2 blocks "sync fine" but no QC checks, no rewards, no finality — silent consensus regression eth/backend.go must call engine_v2.New + SetEngineV2 + forward HookReward via SetHookReward. Reference fix: commit 7daa274b8.
Bypass dispatcher channels filled but never drained Sync stalls after exactly 1 batch — channel back-pressure blocks subsequent fetches Make channels buffered (size 1) and use non-blocking sends with fallback log.

Grep markers to watch for in logs

Any of these appearing in production logs means something's broken:

BAD BLOCK
invalid merkle root
InsertChain failed
XDC TIPSigning state-root bypass
XDC: Setting head to block with valid cached state
XDC: Head state found via
XDC: Found state via PBSS disk layer root
XDC P1: forced trie commit at checkpoint

The "XDC: ... bypass / found via / forced" lines are recovery paths — they fire when consensus or state expected something and didn't get it. In a healthy run they shouldn't appear.

10. Testing loop — per-bundle gate

Don't apply 50 commits then check if it works. Apply one bundle, gate, repeat.

# For each bundle B in order:
git cherry-pick <B-commits>          # or git merge

# Build gate
go build ./... || { echo "BUILD FAIL"; exit 1; }
go vet ./... 2>&1 | grep -v "^#" || true

# Test gate (touched packages only — full suite too slow)
go test -short -count=1 -timeout 120s ./<touched-packages>/...

# Smoke gate (if consensus-critical bundle: XDPoS, state, blockchain, EVM)
./scripts/local-sync-test.sh wipe-stateful
./scripts/local-sync-test.sh start all
sleep 1800   # 30 minutes
grep -E "BAD BLOCK|invalid merkle|XDC.*bypass|InsertChain failed" nodes-local/*.log
# Expect: zero matches

# Parity gate (only after smoke gate passes)
./scripts/validate-canonical-parity.sh -i nodes-local/snapfullpath/geth.ipc -r https://erpc.apothem.network -q
# Expect: PASS  N/N matched

# Commit
git commit -am "xdc: port <bundle name> onto vX.Y.Z"

When the loop fails

  1. Roll back the bundle: git reset --hard HEAD~<bundle-size>
  2. Identify the bad commit by bisecting within the bundle.
  3. Fix the conflict — XDC behaviour wins where XDC: marker is present.
  4. Re-run the loop.

11. Deployment to xdc02, Apothem, Mainnet

The promotion path. Don't skip stages.

Stage 1 — xdc02 chaindata recovery

xdc02 has existing chaindata. The new binary should pick up where the old left off.

ssh xdc02 'cd /mnt/data/workspace/reset-baseline/go-ethereum
  # Pull latest
  git checkout <new-branch> && git pull
  make geth

  # Capture state
  ./build/bin/geth attach --exec "eth.blockNumber" nodes-local/snapfullpath/geth.ipc

  # Graceful stop
  ./scripts/local-sync-test.sh stop

  # Verify clean shutdown (look for "Persisted dirty state" + "Blockchain stopped")
  tail -10 nodes-local/snapfullpath.log

  # Restart with new binary
  ./scripts/local-sync-test.sh start snapfullpath

  # Watch startup logs for XDC: patches + V2 wiring confirmation
  tail -50 nodes-local/snapfullpath.log | grep -E "XDC:|XDPoS V2"
'

Stage 2 — xdc04 fresh-wipe sync

The stronger test — sync from genesis. Exercises every code path including block 2700 BigBalance, TIPSigning at 23.78M, V2 switch at 56.83M.

ssh xdc04 'cd /mnt/data/workspace/reset-baseline/go-ethereum
  git checkout <new-branch> && git pull
  make geth
  ./scripts/local-sync-test.sh wipe-stateful   # wipes chaindata
  ./scripts/local-sync-test.sh start snapfullpath
'
# Expected duration to Apothem head: 45-60h

Stage 3 — 7-day soak

Both nodes at head. Watch ethstats dashboard. Run parity validator daily.

Abort criteria (any one → rollback to xdc-network-pre-reset):

  • Chain divergence (head hash != canonical)
  • Persistent drift > 50 blocks behind
  • Any XDC TIPSigning state-root bypass log fire
  • Any BAD BLOCK record

Stage 4 — Mainnet bring-up

Real value at stake Mainnet has actual XDC tokens transacting. Don't skip Apothem soak. Don't deploy to multiple mainnet nodes at once.
  1. Fresh mainnet sync on isolated host. Same binary. ~60-80h.
  2. Compare head hash to https://explorer.xinfin.network. Must match exactly.
  3. 48h parallel soak at mainnet tip.
  4. Tag erigon-xdc-vX.Y.Z-rc1. Operator runbook in docs/port/HOW_TO_RUN.md.
  5. Canary: 1 mainnet sync node behind load balancer with existing fleet. 7-day watch.
  6. General availability only after canary green.

12. M8 — masternode bring-up (separate workstream)

Block production. Always escalate M8 design to the Opus planner before implementing (per CLAUDE.md).

Prerequisites not in the sync-node port

  • XdcAgent — ~353-line XDC sealing agent (V1 round-robin sealing + V2 BFT vote/timeout cadence). See miner/xdc_agent.go on xdc-network.
  • Full V2 BFT dispatch — handleInboundVote/Timeout/SyncInfo in eth/handler_eth.go must call getOrInitBft().Vote/Timeout/SyncInfo. Requires bft.Bfter plumbing.
  • Broadcast LRU caches — eth/peer.go + peerset.go need knownVotes/knownTimeouts/knownSyncInfos LRU caches and PeersWithoutVote/Timeout/SyncInfo helpers to prevent broadcast storms (Issue #272).
  • peer.SetHead — needed to track peer chain head for syncer wakeups.
  • Private testnet — cross-client validation: mixed geth-XDC + erigon-xdc masternodes producing blocks accepted by each other.

Don't attempt M8 until sync-node bring-up has 7-day soak green on mainnet.
