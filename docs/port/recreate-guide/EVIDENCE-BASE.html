⚠️ Correction to the earlier docs (PBSS version)

My earlier WHY-MODERN-GETH.md/PROPOSAL.md stated PBSS "first shipped in v1.12.1, not 1.13.0." The deep-research evidence (EF release blog + v1.11.0 notes, 3-0 verified) shows that framing was misleading. The accurate picture:

Version Evidence
PBSS deferred (prep PRs only) v1.11.0 (2023-02) v1.11.0 release notes: deferred "so we can get back to a steady release schedule"
Code merged (PR #25963) — present in this tag in v1.12.1 (2023-08-10) local git tag --contains 7de748d3f
PBSS officially shipped (announced, usable) v1.13.0 (2023-09-12) EF blog "geth v1.13.0"
PBSS default for new full nodes v1.14.0 (2024) EF blog / geth docs

Lesson (methodological): "earliest tag containing the introducing commit" ≈ "first release with that code," but for a large multi-PR feature announced later it is not the same as "first release where the feature shipped/was usable/became default." For PBSS specifically, cite v1.13.0 (shipped) / v1.14.0 (default). The other git-derived versions in §4 of WHY-MODERN-GETH.md (freezer v1.9.0, snap v1.10.0, pebble v1.11.0, etc.) are corroborated below.

Verified findings (all primary-sourced unless noted)

1. Freezer / ancients — geth v1.9.0 (Jul 2019) · vote 3-0

Splits the DB: blocks & receipts older than ~90,000 blocks behind head ("3 epochs") move out of LevelDB into an append-only flat-binary "freezer", explicitly so cold data can live on cheaper/durable HDD while recent state stays on SSD. Concrete benchmark: a fresh fast-sync at block 7.77M placed 79 GB in the freezer vs 60 GB in LevelDB. Sources: geth databases doc, EF blog v1.9.0, PR #17814. → Correction (live codebase audit, below): XDPoSChain does NOT have a functional freezer — it runs geth's nofreezedb path (Ancient* return errNotSupported; freezer_table.go is a 34-line error-var stub; no freezer is ever opened). All blocks/receipts live in LevelDB. The freezer is a modern-geth win XDC still lacks.

2. Path-based state storage (PBSS) — shipped v1.13.0, default v1.14.0 · vote 3-0

Replaces the hash-scheme MPT. Implements online pruning by default ("no more guerilla offline pruning"). Offline pruning applies ONLY to the legacy hash scheme and "will be deprecated." Verified in v1.17.3 source: snapshot.go ("only supported in hash mode"), flags.go (--state.scheme hash|path). Sources: v1.11.0 notes, EF blog v1.13.0, geth dbpruning doc. → XDC 2.7.0 (hash-only) predates all state-scheme evolution — this is the single biggest gain from migrating.

3. Hash-scheme nodes grow unbounded; PBSS bounds them — geth docs · vote 2-1 (dissent was a currency quibble)

A snap-synced hash-scheme node needs >650 GB and grows ~14 GB/week with default cache; offline pruning resets it back to ~650 GB. PBSS prunes online, avoiding the prune-and-reset cycle. CAVEAT (currency): these doc figures have drifted upward — independent 2026 sources cite ~1.2 TiB and ~7–8 GiB/week for a fresh hash full node. Use 650 GB / 14 GB-week to illustrate the mechanism, not today's absolute best-case. Sources: geth dbpruning doc, EF blog v1.13.0, 7BlockLabs 2026 disk sizes. → This is the mechanism behind XDC's ~800 GB-and-rising full node and its resync ritual.

4. Snap sync — introduced v1.10.0, default v1.10.4, fast-sync removed v1.10.14 · vote 3-0

Downloads state-trie leaves with range proofs and regenerates the trie locally (vs fetching every intermediate node), plus a state-healing phase. Healing "has to outpace the growth of the blockchain, otherwise the node will never catch up." geth made snap the default and removed fast sync entirely, demonstrating architectural superiority. Sources: geth sync-modes doc, EF blog v1.10.0, devp2p snap spec. → XDC 2.7.0 uses fast sync (node-by-node state download) — slow, and the reason a fresh node takes days.

5. eth wire protocol chain (eth/63 → eth/70), each tied to an EIP · vote 3-0

eth/64 (Nov 2019, EIP-2124/2364 ForkID) · eth/65 (Jan 2020, EIP-2464) · eth/66 (Apr 2021, EIP-2481 request-ids) · eth/67 (Mar 2022, EIP-4938 drop GetNodeData) · eth/68 (Oct 2022, EIP-5793) · eth/69 (Apr 2025, EIP-7642) · eth/70 (Jun 2025, EIP-7975, still Draft). Sources: devp2p eth spec + the individual EIPs. → XDC 2.7.0 sits at eth/62–63, predating every one of these.

6. eth/64 ForkID (EIP-2124/2364) — fixes fragile peering · vote 3-0

Adds forkid:[forkHash:[4]byte, forkNext:uint64] to the Status handshake; forkHash = CRC32 of genesis + all passed fork-block numbers. Incompatible nodes "disconnect before expensive block exchanges and validations," and ForkID-based discovery filtering rejects incompatible peers before dialing. Verified bit-for-bit in core/forkid/forkid.go. Sources: EIP-2124, EIP-2364, PR #31592. → XDC 2.7.0 has no ForkID — it cannot cheaply reject cross-fork/cross-chain peers (the "fragile peering" pain point).

7. eth/66 request IDs (EIP-2481) · vote 3-0

Adds a 64-bit request_id to every request/response pair so clients match responses to requests directly, instead of fragile response-content matching. Sources: devp2p eth spec, EIP-2481. → XDC 2.7.0 predates request-ids — the exact gap that forces the port's custom "no-RequestId bridge."

8. eth/67 dropping GetNodeData (EIP-4938) was the prerequisite for PBSS · vote 3-0

Removed GetNodeData/NodeData (the eth/63 mechanism for serving raw trie nodes by hash). EIP-4938 verbatim: "Avoiding the need to store such a mapping in the database is the main motivation for removing this request type." The v1.13.0 blog confirms the causal chain: with path-based keys "Geth becomes incapable of serving the old fast sync." Sources: EIP-4938, EF blog v1.13.0. → The load-bearing link: you cannot adopt PBSS while still serving GetNodeData. XDC 2.7.0 still serves it → locked into hash-keyed storage. Migrating the wire protocol is a prerequisite for migrating storage.

9. eth/69 (EIP-7642) — history-expiry-aware peering · vote 3-0

Drops the now-meaningless td from Status; adds earliestBlock/latestBlock/latestBlockHash + a BlockRangeUpdate (0x11) message so peers advertise the historical range they can serve. Motivated by the history-expiry decision that clients may drop pre-merge history after May 1, 2025 (EIP-4444 direction). Sources: EIP-7642, EF partial-history-expiry post.

10. The Merge (Sep 15 2022) + Engine API; internal PoW sealing removed v1.14.0 · vote 3-0

PoW→PoS; mining no longer possible on mainnet. EL↔︎CL now talk over a JWT-authenticated Engine API (port 8551). geth v1.14.0 (Apr 2024) removed Ethash/Clique sealing entirely (--mine panics). Sources: EF Merge announcement, execution-apis engine auth, geth #28671. → Relevance to XDC: XDPoS is its own consensus engine, so XDC does not adopt the Engine-API split — but it inherits the dead-PoW-code cleanup. Open architectural question (below): does XDPoS sit as an in-process consensus.Engine (the Clique pattern, which still exists) or need an external driver? Per the project's operating rules this warrants planner escalation.

11. Pebble DB — added v1.11.0 (opt-in), default v1.12.0 · vote 3-0

geth added Pebble to replace/augment LevelDB, citing LevelDB as "a one-person project where the maintainer has signaled that the project is not a priority." Opt-in via --db.engine=pebble in v1.11.0; default in v1.12.0. (v1.11.0 also fixed a snap-sync stale-pivot stall, PR #26453.) Sources: v1.11.0 notes, PR #26517. → XDC 2.7.0 is LevelDB-only.
