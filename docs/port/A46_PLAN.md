## Architectural truth (confirmed from code reading)

The modern v1.17.3 codebase **already merged XDPOS2 into the eth protocol
handler**, matching XDPoSChain's pattern:

- `eth/protocols/eth/protocol.go:45`:
  `var ProtocolVersions = []uint{XDPOS2, ETH70, ETH69}`
- `eth/protocols/eth/protocol.go:35`: `XDPOS2 = 100`
- `eth/protocols/eth/handler.go:284-285`: XDPOS2 routes to `xdpos2` msgHandler map
  (line 207) which has GetBlockHeaders, GetBlockBodies, GetNodeData, GetReceipts,
  + XDPoS V2 consensus messages.
- `eth/protocols/eth/handler.go:111-117`: `MakeProtocols` creates a
  `p2p.Protocol` per ProtocolVersion (so XDPOS2 IS an eth protocol at
  version 100), each calling `backend.RunPeer(peer, ...)`.
- `eth/handler_eth.go:38`: `RunPeer → runEthPeer(peer, ...)`.
- `eth/handler.go:289`: `peer.Handshake(...)` — XDPOS2 uses `handshake62`
  (eth/protocols/eth/handshake.go:92) which validates NetworkID + ProtocolVersion
  + Genesis. Genesis must match.
- `eth/handler.go:313`: `h.peers.registerPeer(peer, snap)` — should register
  XDPOS2 peer into `peerSet.peers`.
- `eth/handler.go:324`: `h.downloader.RegisterPeer(...)` — should register
  in downloader peer set.

## Root cause — CONFIRMED via A.46-diag at verbosity 5 (2026-06-05 IST 06:43)

**Finding:** A.43 (commit `07d144624`) and A.46-diag (same commit) BOTH fail
at the **RLPx (P2P transport) layer** when dialing xdc04 archive (commit
`a119e0b2`). xdc04 returns EOF mid-handshake:

```
TRACE Failed RLPx handshake addr=65.21.71.4:30320 conn=staticdial err=EOF
```

This is BEFORE eth/XDPOS2 handshake. So all hypotheses below about eth-peer
registration are moot — connection never reaches that layer.

**Confirmed:** A.43's `ss -tnp` output shows ZERO peer connections (only ethstats
outbound socket). The "XDPOS2 BlockHeaders/Receipts received peer=75d58040"
lines in A.43's log are **ghost entries** generated by A.14c's seedFastStatePeers
internal loop, not real wire traffic.

**Confirmed:** xdc04's `admin.peers` shows it ACCEPTS connections from same
xdcscan host (the reth/v0.3.1 instance) and from other modern v1.17.3 peers
built from commit `02ebae0d`. But xdc04 REJECTS `07d144624` at RLPx.

**Hypothesis:** Commit `07d144624` (A.14c branch) introduced a change in the
RLPx encrypted handshake codepath that breaks wire-compat with older commits
(`a119e0b2`, `02ebae0d`) on the same v1.17.3 base. Candidates:
- RLPx snappy frame negotiation
- ENR (Ethereum Node Record) signature/fields
- ECIES key-exchange parameters

### Resolution path (replacing all earlier H1/H2/H3 hypotheses)

1. **Bisect commits between `a119e0b2` and `07d144624`** to find the RLPx-
   breaking change. There are 5 commits in that range per `git log
   a119e0b2..07d144624 --oneline`.
2. **Once identified**, either:
   - Revert the breaking change on the A.46 branch (preferred — keeps A.14b/A.14c
     wins), OR
   - Bypass it via a config flag for the production binary

3. **Rebuild A.46 binary** at the corrected commit, redeploy on xdcscan port
   30360, verify `Failed RLPx handshake` lines disappear and real peers appear
   in admin.peers.

4. **All subsequent A.46 plan steps (downloader peer-set wiring, skeleton
   bridging, etc.) become unnecessary** if RLPx works — the existing A.1-A.42
   machinery will engage naturally because XDPOS2 peers will then flow
   through the normal runEthPeer → registerPeer → downloader.RegisterPeer
   chain.

## (Original H1/H2/H3 hypotheses — superseded by finding above, kept for reference)

Connection IS established (TCP handshakes, P2P session up, messages
flowing) but the peer **never makes it into `peerSet.peers`**. Two
candidates:

**H1: handshake62 silently fails on XDPOS2's Genesis or NetworkID check
post-A.X changes.** The xdc04 archive runs same v1.17.3 codebase, so
genesis SHOULD match. But — A.43 binary is commit `07d144624` and xdc04
archive is `a119e0b`. Different commits → could be different chain config
→ different genesis hash → handshake fails.

**H2: handshake62 succeeds, registerPeer succeeds, then peer immediately
unregisters via `defer h.unregisterPeer(peer.ID())` at handler.go:317
because `handler(peer)` (line 387) returns immediately.** The handler is
`eth.Handle` (handler.go:121) which loops `handleMessage` until error. If
the very first incoming message hits an error-returning XDPOS2 handler,
the handler returns, runEthPeer returns, peer unregisters.

**H3: connection NEVER goes through runEthPeer at all.** There's some
XDPOS2-specific bypass (e.g., the trusted-staticdial path of p2p/server.go
might use a different protocol path). Not seen in code review but worth
verifying.

Restart A.43 with `--verbosity 5` (Trace level). All peer registration

Single restart, single log read.

## Fix plan (in priority order, only after diagnosis confirms)

### Fix A — if H1 (handshake fails on cross-commit XDC config divergence)

The genesis hash difference between commits is the most likely cause. Look
at `chainspec` / `xdc.go` / `params` differences between `07d144624` and
`a119e0b`. The XDC chain config carries XDPoS V1/V2 switch blocks,
masternode configs, reward constants. If any of these encode into the
canonical-mainnet genesis differently, genesis hash diverges.

Fix: ensure A.43 and xdc04 binaries are built from the same commit. Rebuild
xdc04's archive with `07d144624` (or rebuild A.43 to match `a119e0b`'s
chain config). **Lowest LOC option but requires xdc04 rebuild** — and
user explicitly said don't touch xdc04.

Alternative: rebuild A.43 from `a119e0b` (xdc04's commit) so handshake
matches. ~5 LOC change (revert any post-`a119e0b` consensus-touching code
on the A.43 build) + full rebuild.

### Fix B — if H2 (handshake OK, but XDPOS2 handler returns error early)

Look at handleMessage's first invocation. The first message after handshake
is typically GetBlockHeaders (downloader probes the peer). If the XDPOS2
GetBlockHeaders handler returns an error, the peer drops. Likely culprits:
A.X-era code that returns errors for malformed RequestId in xdpos2 wire shape.

Fix: harden xdpos2 handlers to never return non-nil error post-handshake
(log + return nil for malformed messages, drop the request but not the
peer). ~30 LOC across xdpos2 message handlers in `eth/protocols/eth/handler.go`.

### Fix C — if H3 (bypass path exists)

Find the bypass and route XDPOS2 peers through runEthPeer. Could be a
single-line p2p.Server config change. ~10 LOC.

### Fix D — fallback: explicit XDPOS2-peer-to-eth-peerSet bridge

If the above don't apply, add a new helper:

```go
// In eth/handler.go or new file eth/handler_xdpos2_bridge.go:
func (h *handler) RegisterXDPOS2Peer(peer *eth.Peer) error {
    // Force-register an XDPOS2-protocol peer into the eth peerSet so
    // downloader/skeleton can use it as a header/body/receipt source.
    if err := h.peers.registerPeer(peer, nil); err != nil {
        return err
    }
    if err := h.downloader.RegisterPeer(peer.ID(), peer.Version(), peer); err != nil {
        h.peers.unregisterPeer(peer.ID())
        return err
    }
    return nil
}
```

Wire this into the XDPOS2 protocol handler so that, on successful XDPOS2
handshake, peers register even if the standard runEthPeer flow rejected
them. ~50 LOC across `eth/protocols/eth/handler.go` and `eth/handler.go`.

## Why this should work

The user's empirical observation that XDPoSChain v2.7.0 reaches tip and
follows the chain via the SAME peer fleet PROVES the network supports
fast-sync. The blocker in modern v1.17.3 is a peer-set bookkeeping issue,
not a fundamental protocol incompatibility. Once peer-set bookkeeping is
fixed, the existing A.1–A.42 code paths take over (header dl, body/receipt
fetch, processFastSyncContent → syncFastState → trie sync). All that
machinery already exists and works in isolation — A.14c proved peers
flow into the state-sync pool. We just need the same flow into the
skeleton/downloader peer set.
