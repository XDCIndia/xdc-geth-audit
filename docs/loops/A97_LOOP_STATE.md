### PROPOSE-FORK RCA VERDICT — TRANSIENT V1 MULTI-SIGNER RACE (not a code bug)

**Simulation results (read-only eth_call + debug_traceCall):**
All 4 nodes returned **identical** results for simulate propose(0xd9D7628...):
- eth_call result: `0x` (success, no revert) on all nodes
- debug_traceCall gasUsed: **202173** on all 4 nodes (NODE1=202173, NODE2=202173, NODE3=202173, NODE4=202173)
- No divergence in execution — the EVM call is fully deterministic

**Root cause: V1 Clique-PoA voting mechanism + propose tx timing**

In V1, propose() is NOT a special transaction (IsSpecialTransaction() returns false for 0x88 —
only 0x42=BlockSigners and 0x3D=RandomizeSMC qualify). The propose() call to 0x88 is a NORMAL
user tx. This means:

1. The tx was sent while the chain was mid-block (multiple nodes were simultaneously computing
   the next block after 762), so different nodes received the tx in their mempools at different
   times relative to block 763 construction.

2. In V1 (clique-PoA), any authorized signer can produce block 763. The in-turn signer
   (difficulty=N) produces immediately; out-of-turn signers (difficulty=N-k) wait k*2s.
   If the in-turn signer's block propagates late, TWO OR MORE out-of-turn signers may produce
   competing blocks.

3. The propose() tx itself is deterministic (gasUsed=202173 identical across all nodes). But
   because the tx was in-flight during block 763 construction, nodes disagree on WHETHER the
   tx is in block 763 or arrives in the mempool AFTER block 763. This produces:
   - Node A: block 763 contains the propose tx → state root X
   - Node B: block 763 does NOT contain the propose tx → state root Y
   - Node C: received a competing block 763 from another signer → state root Z

4. The KYC uploadKYC() call (a string arg with variable-length ABI encoding) is also a normal
   tx. It is also deterministic in execution but timing-sensitive for inclusion.

5. With 4 nodes (N=4), V1 requires only 2 votes (>N/2 = >2) to add/remove a signer. The
   propose() tx changes validator state at 0x88. Any node that INCLUDED it in block 763 got
   a different contract state than nodes that DID NOT. This is NOT non-determinism in EVM
   execution — it is non-determinism in tx ORDERING ACROSS THE 3-WAY FORK.

**Evidence for "transient race, not a code bug":**
- Simulation: All 4 nodes give identical gasUsed=202173, no revert. EVM is deterministic.
- After setHead(762) + miner.restart: chain re-converged cleanly at block 770.
- The propose() tx was sent at a sub-optimal time: during active block production at block ~762-763,
  with multiple in-turn/out-of-turn candidates simultaneously building the next block.
- Code review: `IsSpecialTransaction()` at XDPoSChain/core/types/transaction.go:485-491 only
  covers 0x42 and 0x3D (BlockSigners + RandomizeSMC). 0x88 (MasternodeVotingSMC) is NOT
  a special tx — it has NO ordering guarantee, NO gasless treatment, NO replay protection
  in the V1 block production path.

**Code references (XDPoSChain, read-only):**
- `core/types/transaction.go:485-491` — IsSpecialTx() gate excludes 0x88
- `consensus/XDPoS/engines/engine_v1/engine.go:699-715` — Prepare() picks votes via
  `rand.Intn(len(addresses))` — this is for the clique *header coinbase vote* (separate from
  the propose() EVM call), and is intentionally random per the clique spec
- `consensus/XDPoS/engines/engine_v1/engine.go:953-963` — calcDifficulty() shows V1 is
